一、背景与目标

为什么要做这件事 · 要解决什么问题

1.1 现状痛点：只给结论、不给原因

构建详情页原来只有一个孤零零的状态词 —— 「失败」「已取消」「运行中」。用户看到这个词之后， 还得自己去翻编排图、逐个点开 Job 和插件，才能搞清楚三件事：

用户的疑问现状代价
是谁取消的？状态一律显示「已取消」，分不清用户手动取消、系统取消，还是父流水线连带取消翻取消人、翻父流水线，跨页面跳转
哪一个插件失败了？只知道构建失败，不知道是执行失败、质量红线、人工审核驳回，还是子流水线挂了逐个 Job 展开，找红色图标
现在卡在哪？「运行中」背后可能是排队、等构建机、等人工审核，页面完全不区分只能干等，或去别处查队列

1.2 方案目标：多给一张会说话的卡片

在同一条详情接口 getBuildRecordByExecuteCount 上，额外返回一张状态小结卡片： 还没结束时说清现在卡在哪一步、前面有谁在排队、有没有需要人介入的环节；已经结束时说清为什么结束 （取消 / 失败 / 超时 / 成功）、原因是什么、影响了哪些 Stage / Job / 插件。前端完全按后端给出的大类 （endCategory / runningCategory）和已翻译文案渲染， 不自己猜成因。

图 1 状态小结卡片的三张典型形态：排队等位 / 失败溯源 / 等待人工，都用同一张卡片承载

1.3 上线结论

可以上线。终态大类与页面状态对齐，FastKill、阶段准入和取消人的口径与实现一致。第 10 节的三段展示窗口是 推送时序导致的正常空窗，不是状态写错。注意 biz-base 依赖 jOOQ 连库生成，需在 CI 再编一次。

二、核心设计思路

四条原则 · 后面所有的流程图和模块分工，都从这四条推导出来

2.1 四条设计原则

原则 1

一张卡片，两种寿命

结束原因确定后不再变，写入记录的 modelVar["buildEndInfo"]； 排队和执行中的等待每秒都在变，不落库，打开详情时现算 buildRunningInfo。

同一时刻只返回其中一张，避免两张卡片叠在一起。

原则 2

构建级大类跟着页面状态走

卡片大类必须和页面左上角状态是同一类：取消对取消、失败对失败、排队超时对超时、成功对成功。

Job 超时、步骤超时、构建机失联发生在某个位置上，构建本身往往以失败或取消收尾， 所以构建级卡片不叫「超时」，超时分钟数写在原因和那一行位置上。

原则 3

能提前记的成因提前记，但运行中不展示

用户一点取消，取消人、在途插件就固定了；Job 超时、构建机失联也是在当时才知道影响了哪个容器。这些先写入记录。

构建还在跑时，读取直接不返回这张卡片；等构建真正结束后，再按最终状态决定保留、覆盖或清掉。

原则 4

阶段准入把「记录」和「历史」拆开看

审核挂起时，记录和历史都是 STAGE_SUCCESS，卡片是「审核中」。最后一组点同意后， 记录先变运行，历史表要等事务提交才变运行。

运行态看的是历史表，所以要等历史提交后再推一次详情。驳回时记录必须保持 CANCELED， finally 才能在「已取消」前提下跑完收尾阶段。

一句话记住这四条。终态是「一次写、永不变」的结论，运行态是「每次读、现算」的快照； 构建级只说大类、位置级才说细节；成因要在现场记下来、但别提前给用户看； 阶段准入期间两张表短暂不一致是正常的。

2.2 整体数据流转架构

写入 → 存储 → 读取：成因在何时写入，读取时又按什么决定返回哪张卡片

整个方案围绕「写入 → 存储 → 读取」三条链路展开。成因在事件发生时写入、或在构建结束时解析； 存储分为终态详情（落库）和运行状态（历史表）；读取时按记录状态决定返回哪张卡片。

图 2 整体数据流转架构：成因在「发生时」或「结束时」写入，读取时按状态决定返回哪种卡片
层次承载什么关键点
写入层 取消 / 超时 / 心跳失联 / 暂停终止；构建结束时的统一解析 成因「当场可知」就当场写（取消人、在途插件、失联容器）；「要等结果」的留给构建结束统一对齐
存储层 构建记录 modelVar：终态详情 buildEndInfo（落库）
构建历史 status：排队还是运行（实时）		 终态落库、运行态不落库。运行态若落库读到的必然是过期快照，还会造成严重写放大
读取层 接口 getBuildRecordByExecuteCount → 详情页一张卡片 终态为空才算运行态，保证两张卡片互斥；前端「哪个非空渲染哪个」，不要两张叠着画

两套卡片互斥、字段语义不同。终态 buildEndInfo 描述「为什么结束、跳到哪」， 覆盖成功 / 失败 / 取消 / 排队超时 / 阶段准入审核中；运行态 buildRunningInfo 描述 「此刻卡在哪、在等谁」，覆盖排队中与执行中。两者不共用同一套位置结构。

3.1 页面状态与返回卡片对照表

四种页面形态，对应四种判定路径
用户看到的页面记录状态返回卡片
在排队、在执行 QUEUE / QUEUE_CACHE / 运行中 buildRunningInfo
阶段准入等人审核 STAGE_SUCCESS，且审核组仍是 REVIEWING buildEndInfo，类型 SUCCESS_STAGE_REVIEWING
成功、失败、取消、排队超时 对应终态 buildEndInfo
最后一组刚点同意、历史还没提交 记录已是运行，或仍是阶段挂起；
历史仍是阶段挂起		 这一帧可能两张都空，见第十章空窗①

三个容易忽略的点

记录表是锚点

不用历史表判终态。构建结束的瞬间，记录已经是终态，历史表可能还显示运行中——若用历史表，这一下推送会算不出终态卡片。

「有」不等于直接用

库里已有终态详情时，还要校验大类是否与记录状态同类。一致才刷新位置后返回，不一致要覆盖、重写或丢弃后重算。

两张卡片互斥

组装详情时先看终态是否非空：终态非空才算终态，否则才去现算运行态。前端也按「哪个非空渲染哪个」。

实现落点：PipelineBuildFacadeService 组装详情时， 仅当 buildRecord.buildEndInfo == null 才会调用 buildRunningInfoResolver.resolve(...) 现算运行态——这就是互斥的唯一开关。

5.1 写入时序

终态详情的写入分两个时机：

  • 成因已明确时提前写入：如用户取消、Job 超时、构建机失联。
  • 构建结束时统一对齐：失败、阶段驳回、排队超时。普通成功不写库，打开详情时合成。
图 5 终态写入时序：提前写成因 → 构建结束时对齐 → 再推一次保证卡片一致

关键设计：取消人在发出取消事件「之前」就写入记录。 因此父流水线级联能读到真实操作人。没有真实操作人时，记录更新会写入字面量 System，读取时当成系统取消，不会展示成某个用户取消的。

5.3 几个容易踩坑的细节

这几条都是「不这么写就会出错」的地方

① 运行中重试要清掉上一轮

重试一开始就清掉本轮已写下的终态，避免上一轮的失联或 Job 超时挡住这次结束时的写入。

否则：重试后的构建会带着上一轮的失败卡片。

② Job 超时连续打到多个 Job

后一次把模型里仍处于取消 / 暂停的插件并进已有卡片，不把已失败的改回取消，也不覆盖用户取消。

否则：第二个 Job 超时会把用户取消刷成系统取消。

③ 插件被强制终止但自己没有错误码

用事件里的终止原因替换引擎的占位错误码；插件已经报了自己的错误码就保留插件的。

否则：被失败即停连带停掉的人工审核，会被说成「审核驳回」。

④ 子流水线启动时先记名字

子流水线启动时把名称和构建号一并记下。旧数据没有名称时，失败行用兜底文案。 构建号不写进原因句子，前端用子流水线信息做跳转。

否则：跨项目跳转会 404。

这三条的共同模式。写入侧面对的是「成因可能被多次追加」的现实，所以每条写入都必须是 幂等且不降级的：可以补细节，不能把更准确的信息覆盖成更模糊的。

构建级失败类型怎么定 · FastKill 与多类失败

6.1 判定举例

为什么需要「多类失败」这个大类

为什么需要「多类失败」？如果 FastKill 那一行跟构建级用同一种单一失败， 页面会把整行画成错误码 2199010，设计稿里的「因失败即停被终止」就出不来。

所以只要 FastKill 和别的失败同时存在，构建级就写成「多类失败」—— 这是页面开关，不是说有很多个互不相关的根因。

位置上有什么构建级类型
只有一个插件执行失败执行失败
只有步骤超时，构建状态是失败执行失败（该行仍写「步骤超时」+ 分钟数）
步骤超时 + Job 超时执行失败（两行位置各自保留超时类型）
一个插件失败，同阶段其它 Job 被失败即停终止多类失败（被终止行写「因失败即停被终止」）
只有失败即停、没有别的失败行执行失败
红线未达标 + 插件失败多类失败
一个位置都收集不到（如互斥锁没抢到）执行失败（仍给一张卡，否则详情打不开）
构建状态本身是排队超时排队超时（不走上面的失败汇总）

6.2 原因归谁：构建级 vs 位置级

失败卡片的构建级原因留空

因为同一次构建可能有多处失败，取其中一条会和位置列表打架。

例外：排队超时的原因对整次构建只有一份，留在构建级。

细节都写在该行位置上

每行自己的驳回意见、红线指标、子流水线名、超时分钟数，都写在该行上。

展示时卡片原因压缩空白后截到 200 字，插件原始错误只放 tooltip。

容量边界：位置最多 50 条，单条原因最长 512 字， 展示截断到 200 字（超长补「...」），插件原始错误上限 512 字。

7.1 读取时的关键规则

三类校正 · 国际化 · 重算规则的一致性

取消合成：看取消人是谁

取消人有值且不是 System，就是用户取消；否则是系统取消。

用户取消文案里的「N 处」要与卡片上的位置条数对齐。

执行前暂停被终止的那一行，状态文案用「暂停 / 终止」，不用笼统的「取消」。

国际化：库里存码，不存句子

reasonCode 在读的时候按请求语言翻译。

库里存的是码和参数，不是某一门语言的句子——这样切语言不需要重写数据。

三类「大类对不上」分别怎么处理

对不上的情况处理方式为什么
失败对不上用模型里的失败位置重写失败卡片；系统取消和父流水线的原因可以留下失败位置只有编排模型最全，落库的可能不全
排队超时对不上改成排队超时构建状态本身是 QUEUE_TIMEOUT，卡片必须同类
成功或取消对不上丢掉这份落库，按状态重新合成这两类没有位置细节可捞，重算最干净

读取重算和写入用同一套规则，出现在三个地方：老构建没有落库、取消卡片被按失败重写、 失败卡片又补上了暂停或审核位置。

8.1 关键规则

挂起 · 驳回 · 真正结束三种情形的不同处理

挂起时：不走运行态

  • 位置从 1 开始编，触发器阶段不算。
  • 卡片上有审核组序号、组名、待审核人和已等待时长（waitCostTime）。
  • 合成入口：PipelineBuildRecordService 中按 stage.checkIn / checkOut 里 status == REVIEWING 定位审核阶段。

驳回时：不能把记录改成运行

记录一旦进入已取消，后续普通更新改不动这个状态，finally 期间详情才能稳定停在已取消。

历史表改回运行是原有调度需要（为了把 finally 跑起来），和详情卡片用的不是同一张表。

真正结束时：buildEnd 直接写最终状态

  • buildEnd 不受「已取消之后不能再 update」这条限制。
  • 若阶段上有驳回记录且整体成功，写入 SUCCESS_STAGE_ABORT。

九、运行态实时计算

排队和执行中现算什么 · 不落库的原因

运行态只看历史表。排队是 QUEUE / QUEUE_CACHE， 执行中是运行中的那些状态。阶段挂起、触发待审核、已经结束，这里直接返回空。 计算抛错也返回空——详情页仍然打得开。

图 9 运行态计算流程：排队分「并发组 / 普通」，执行中分「有 Job 等待 / 正常推进」

为什么运行态不落库？排队位置、前方排队列表、已等待时长每秒都在变， 落库读到的必然是过期快照，还会造成严重写放大。

所以只在「读取详情且构建未结束」时现算——对已结束的构建零额外开销。

10.2 三段已知空窗

只影响中间某一帧 · QA 按这个预期看，不是 bug

结论先行：最终落库是对的。这三段只影响中间某一帧的展示，都属于推送时序导致的正常空窗。

空窗 ①

最后一组点同意后

审核结果刚落库的那一次推送会空一帧。

记录还是阶段挂起，历史还没改回运行，模型里已经没有「审核中」—— 既不是审核中，也不是执行成功。

随后：历史提交后的推送变成「执行中」。

空窗 ②

驳回之后、finally 跑完之前

详情是「已取消 / 系统取消」，历史列表可能已经显示运行中。

随后：构建结束后才变成「阶段准入驳回」。

空窗 ③

驳回并以阶段成功收尾

构建结束会先推一次。这时终态还没写入，历史仍是运行中，可能先闪一张运行中卡片。

随后：同一次结束流程里的下一次推送才是阶段准入驳回。

空窗对照：一帧之后会变成什么

空窗这一帧用户可能看到下一帧
①两张卡片都空执行中（RUNNING_NORMAL）
②已取消 / 系统取消（历史列表可能显示运行中）阶段准入驳回（SUCCESS_STAGE_ABORT）
③先闪一张运行中卡片阶段准入驳回

给 QA 的提醒：这三段不要报「状态写错」。判断标准是 最终落库的大类与页面左上角状态一致，而不是中间某一帧是否出现过渡态。

十二、明确不改的行为

这些边界刻意保留 · 不要在后续迭代中误改
不改的行为原因
不在构建结束时扫仍停在 QUEUE / QUEUE_CACHE 的任务并改引擎状态 那次扫描赶不上取消后已经卡住的 Job，也会和还在认领任务的构建机不一致
单个插件变成取消时，不删 CANCEL_ACTION_TIME 标记 60 秒后第二次取消会不会升级成强制终止，靠这个标记判断
服务关闭、删除流水线、编排不存在，维持原来的构建状态，只补原因 这些入口原来的构建状态有其语义，不应被详情卡片改写
stageCancel 继续把记录写成已取消 这是取消动作，记录需要停在终态上，finally 才能稳定跑完

为什么单列一章。这四条看起来像「实现得不彻底」或「可以顺手优化」的地方， 但实际上每一条都有明确的时序或一致性问题作为理由。改动它们会引入更难查的 Bug。
